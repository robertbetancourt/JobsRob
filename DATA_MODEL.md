# DATA_MODEL.md

## Purpose

Define the data structures used by Job Radar.

The model should support:

- Job discovery
- Source normalization
- Duplicate detection
- Hard filtering
- AI evaluation
- Human review
- Saved opportunities
- Application tracking
- Company tracking
- Future feedback-based scoring improvements

The MVP is local-first and single-user.

---

# 01 — Design Principles

## Source data vs derived data

Keep original job information separate from information generated by Job Radar.

### Source data

Facts obtained from a job source:

- Title
- Company
- Description
- Location
- Salary
- Employment type
- Source
- URLs
- Posted date
- Application questions when available

### Derived data

Information produced by the system:

- Duplicate grouping
- Hard-filter results
- AI score
- AI verdict
- Reasons
- Risks
- Application effort estimate
- Recommended portfolio projects
- Robert's decision
- Rejection reason

Never overwrite source information with AI interpretation.

---

# 02 — Job Entity

A `Job` represents one canonical job opportunity.

Suggested structure:

```json
{
  "id": "job_123",
  "title": "Senior Product Designer",
  "company_id": "company_456",
  "description": "...",
  "location": {
    "raw": "Remote - Latin America",
    "country": null,
    "region": "Latin America",
    "city": null
  },
  "work_arrangement": "remote",
  "employment_type": "full_time",
  "seniority": "senior",
  "salary": {
    "min": 2500,
    "max": 3500,
    "currency": "USD",
    "period": "month",
    "raw": "$2,500–$3,500/month"
  },
  "experience_required": "5+ years",
  "source_ids": [],
  "canonical_url": "...",
  "application_url": "...",
  "posted_at": null,
  "discovered_at": "...",
  "last_seen_at": "...",
  "status": "new"
}
```

The exact implementation may change.

---

# 03 — Job Source

A job can be discovered from multiple sources.

A `JobSource` records where a posting was found.

```json
{
  "id": "source_123",
  "job_id": "job_123",
  "source_name": "Greenhouse",
  "source_type": "ats",
  "source_url": "...",
  "application_url": "...",
  "external_id": "12345",
  "discovered_at": "..."
}
```

Possible source types:

- ats
- job_board
- search_engine
- company_careers
- other

The model should not assume a specific provider.

---

# 04 — Company Entity

A `Company` represents the organization hiring.

```json
{
  "id": "company_456",
  "name": "Example Company",
  "website": "...",
  "careers_url": "...",
  "company_type": "startup",
  "industry": "SaaS",
  "location": "...",
  "description": "...",
  "created_at": "...",
  "updated_at": "..."
}
```

Optional future fields:

- employee_count
- funding_stage
- headquarters
- remote_policy
- saved
- notes

Company prestige should not be treated as a major score input.

---

# 05 — Salary

Salary requires structured and raw representations.

```json
{
  "min": 1500,
  "max": 2500,
  "currency": "USD",
  "period": "month",
  "is_estimated": false,
  "raw": "$1,500–$2,500/month"
}
```

Possible periods:

- hour
- day
- week
- month
- year
- project
- unknown

Possible states:

- disclosed
- undisclosed
- estimated
- unclear

Do not invent salary when it is not present.

---

# 06 — Working Conditions

Working conditions should be represented independently from compensation.

```json
{
  "hours_per_day": null,
  "hours_per_week": null,
  "schedule": "Flexible",
  "timezone": "EST",
  "weekend_required": false,
  "after_hours_expected": false,
  "on_call": false,
  "notes": "..."
}
```

The system may not know every field.

Unknown values should remain `null` or `unknown`.

---

# 07 — Location

Location needs more detail than a simple country string.

```json
{
  "raw": "Remote - Americas",
  "work_arrangement": "remote",
  "countries": [],
  "regions": ["Americas"],
  "timezone_requirements": [],
  "residency_required": false,
  "work_authorization_required": false,
  "relocation_available": false
}
```

Possible work arrangements:

- remote
- hybrid
- onsite
- unknown

Important distinction:

- Remote from anywhere
- Remote within a specific country
- Remote within a region
- Remote with timezone restrictions

These should not be treated as equivalent.

---

# 08 — Requirements

Store important job requirements in structured form where possible.

```json
{
  "years_experience": {
    "min": 4,
    "max": null
  },
  "degree_required": false,
  "skills": [
    "Figma",
    "Product Design",
    "UX"
  ],
  "languages": [],
  "work_authorization": [],
  "other": []
}
```

Raw job description remains the source of truth.

Structured requirements are extracted data and may be imperfect.

---

# 09 — Application Requirements

This is important because application effort is part of Job Radar's decision model.

```json
{
  "application_url": "...",
  "ats": "greenhouse",
  "estimated_effort": "low",
  "estimated_minutes": 8,
  "cover_letter_required": false,
  "portfolio_required": true,
  "references_required": false,
  "questions_count": 4,
  "take_home": {
    "required": false,
    "estimated_hours": null
  },
  "video_required": false
}
```

Possible effort values:

- low
- medium
- high
- very_high
- unknown

---

# 10 — Hard Filter Result

Hard filtering should be stored separately from AI scoring.

```json
{
  "status": "pass",
  "reasons": [],
  "warnings": []
}
```

Possible statuses:

- pass
- fail
- review
- unknown

Example:

```json
{
  "status": "fail",
  "reasons": [
    "Unpaid position"
  ]
}
```

Another example:

```json
{
  "status": "review",
  "reasons": [],
  "warnings": [
    "Work authorization requirements unclear"
  ]
}
```

---

# 11 — AI Evaluation

AI evaluation should be structured and explainable.

```json
{
  "score": 91,
  "verdict": "strong_match",
  "dimensions": {
    "role_fit": 23,
    "compensation_conditions": 22,
    "location": 15,
    "experience": 9,
    "scope": 9,
    "application_effort": 4,
    "company": 4,
    "risk": 5
  },
  "why_it_matches": [
    "Product Design role",
    "Remote Latin America",
    "Fintech experience relevant",
    "Experience requirement aligns"
  ],
  "concerns": [
    "Salary range not fully confirmed"
  ],
  "recommended_projects": [
    "B89",
    "Banexcoin"
  ],
  "evaluated_at": "..."
}
```

The exact dimensions and weights remain configurable.

Do not hard-code final scoring weights until tested against real jobs.

---

# 12 — AI Verdict

Possible values:

- apply
- strong_match
- review
- low_priority
- skip

The verdict is a recommendation.

It does not automatically trigger an application.

---

# 13 — Duplicate Detection

Duplicate detection needs to preserve relationships instead of simply deleting records.

Suggested structure:

```json
{
  "duplicate_group_id": "dup_123",
  "canonical_job_id": "job_123",
  "source_job_ids": [
    "source_1",
    "source_2",
    "source_3"
  ],
  "confidence": 0.96
}
```

The system should attempt to recognize:

- Same company
- Same title
- Same description
- Same location
- Same application URL
- Same external ATS ID

A duplicate should not result in losing useful source information.

---

# 14 — Robert Review

Human decisions should be stored separately from AI evaluation.

```json
{
  "decision": "apply",
  "reason": null,
  "notes": "...",
  "decided_at": "..."
}
```

Possible decisions:

- apply
- save
- skip
- review_later

Possible reasons:

- compensation
- location
- work_authorization
- working_hours
- scope
- seniority
- application_effort
- company
- suspicious
- not_interesting
- other

AI and human decisions must remain separate.

---

# 15 — Application

An `Application` tracks what happened after Robert decided to pursue a job.

```json
{
  "id": "application_123",
  "job_id": "job_123",
  "status": "applied",
  "applied_at": "...",
  "next_action": null,
  "next_action_date": null,
  "notes": "..."
}
```

Possible statuses:

- preparing
- applied
- interview
- challenge
- offer
- rejected
- withdrawn

The MVP should not become a full ATS.

---

# 16 — Company Tracking

Companies can be saved independently of individual jobs.

```json
{
  "company_id": "company_456",
  "saved": true,
  "reason": "Interesting remote product company",
  "notes": "...",
  "last_checked_at": "..."
}
```

Future functionality can detect when a saved company publishes a relevant role.

---

# 17 — Feedback

Robert's feedback can later improve the system.

```json
{
  "job_id": "job_123",
  "decision": "skip",
  "reason": "application_effort",
  "created_at": "..."
}
```

Feedback should be used for analysis and future scoring improvements.

The system should not silently change important filtering rules based on a single decision.

---

# 18 — Timestamps

Important entities should include timestamps where useful.

Recommended:

- created_at
- updated_at
- discovered_at
- posted_at
- last_seen_at
- evaluated_at
- decided_at
- applied_at

Store timestamps in a consistent format.

---

# 19 — Data Provenance

Whenever possible, derived information should retain enough provenance to explain where it came from.

For example:

```json
{
  "salary": {
    "value": 2500,
    "source": "job_description",
    "confidence": "high"
  }
}
```

This becomes increasingly important once multiple sources and AI extraction are involved.

---

# 20 — Unknowns

Unknown data must remain explicitly unknown.

Use:

- null
- unknown
- not_available

depending on implementation.

Never replace missing information with guesses.

Examples:

- Unknown salary
- Unknown timezone
- Unknown applicant count
- Unknown team size
- Unknown benefits

The UI should communicate meaningful unknowns clearly.

---

# 21 — MVP Data Requirements

Phase 1 mock data should contain enough variety to test the product.

Include at least:

1. Excellent remote international Product Designer role.
2. Good LATAM opportunity.
3. Low salary but excellent working conditions.
4. High salary but extreme workload.
5. US-only role requiring authorization.
6. Unpaid opportunity.
7. Unknown salary.
8. Junior role with strong compensation.
9. Senior role with poor conditions.
10. Long take-home challenge.
11. Duplicate job appearing from multiple sources.

This dataset should test the decision model rather than merely make the UI look populated.

---

# 22 — Local Persistence

The MVP should persist data locally.

The initial implementation can use a simple local database such as SQLite.

The exact storage layer should be chosen during implementation based on the chosen stack.

No cloud database is required for Phase 1.

---

# 24 — Data Integrity Principles

1. Never fabricate job information.
2. Never overwrite source facts with AI interpretation.
3. Keep AI evaluation versionable.
4. Keep Robert's decisions separate from AI decisions.
5. Preserve duplicate source relationships.
6. Preserve original URLs.
7. Preserve raw salary/location text when structured extraction is uncertain.
8. Allow missing information.
9. Prefer reversible data transformations.
10. Keep the model simple until real usage proves additional complexity is necessary.
